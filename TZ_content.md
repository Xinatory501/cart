1.2. Правила присвоения статуса

Статус

Толкование

Реализовано

Функция присутствует в анализируемом коде и не требует изменения в рамках данного ТЗ. До приемки выполняются smoke- и регрессионные тесты на стенде.

Требуется доработка

Функция отсутствует, реализована частично, содержит дефект, не отвечает целевой архитектуре либо не соответствует требованиям безопасности и эксплуатации.

Ограничение аудита. статус «Реализовано» означает наличие функции в коде, но не заменяет функциональное тестирование с реальными токенами Telegram, AI-провайдерами, web-клиентом и рабочей группой поддержки.

2.2. Целевая архитектура

Одна основная кодовая база с общими модулями core, Telegram, web, AI, case management, localization, integrations и observability.

Каждый проектный профиль связывается с версией общего core-артефакта, выпускается как отдельная конфигурация и разворачивается независимо.

CartaMe_BY, NIVEA_KZ, SQB_UZ и каждый новый бот имеют отдельные Telegram token, БД PostgreSQL или изолированную схему по утвержденной политике, объектное хранилище, домен/API, набор секретов, AI-конфигурацию, группу поддержки, KB, журналы и резервные копии.

Недопустим доступ экземпляра одного проекта к данным, вложениям, очередям, темам, отчетам или секретам другого проекта.

Региональные отличия задаются проектным профилем и подключаемыми адаптерами. Копирование и ручное расхождение ветвей core-кода не допускается.

Новые боты создаются из шаблона BUSINESS или BANK через административный контур. Создание профиля, подключение Telegram token, проверка конфигурации и активация не требуют отдельной ветки исходного кода.

4. Управление регионами, проектами и языками

4.1. Модель релиза

Каждый бот получает отдельный INSTANCE_ID, проектный профиль и независимый жизненный цикл развертывания. В одном регионе может работать несколько ботов разных бизнесов и банков. Версия экземпляра состоит из версии core, регионального профиля, шаблона и проектного профиля, например `core 2.0.0 + region BY 1.0.0 + template BUSINESS 1.0.0 + profile CLIENT_BY 1.0.0`. Обновление одного экземпляра не должно автоматически изменять другие боты этого или другого региона.

отдельные Telegram bot token и username;

отдельные PostgreSQL database/schema credentials и bucket/prefix вложений;

отдельные support group/topic settings, Bitrix24 queue/project и critical alert destination;

отдельные AI provider policy, secrets, models, system prompts и KB index;

отдельные consent/privacy documents, retention policy, timezone, calendar и SLA;

отдельные dashboards, alerts, backups, audit logs и release rollback.

5. Пользовательский сценарий и жизненный цикл кейса

5.1. Первый запуск

Бот показывает название проекта, краткое назначение и кнопки языка.

После языка отображаются privacy/consent documents проекта. Без обязательного согласия функции, требующие PII/API lookup, недоступны; общая справка может оставаться доступной.

После согласия отображается welcome message, start menu и понятная кнопка создания обращения.

Бот не просит лишние данные и объясняет, какие идентификаторы допустимы. Для SQB явно запрещается отправлять PIN, CVV, OTP и полный номер карты.

5.2. Создание и ведение обращения

Кейс создается атомарно и получает уникальный шестизначный ticket в пределах экземпляра. При исчерпании пространства номеров должна быть предусмотрена расширяемая схема без коллизий.

В кейсе фиксируются instance, channel, user identity, language, consent version, source campaign, category, priority, status, owner, AI state, SLA timers и integration correlation IDs.

AI отвечает по KB и разрешенным API. При недостатке данных задает не более разумного числа уточнений и предлагает оператора.

При вызове оператора кейс попадает в очередь; пользователь получает подтверждение, график и ожидаемое время первой реакции по правилам проекта.

После решения оператор выбирает resolution reason, при необходимости отправляет итог и закрывает кейс. Пользователь может подтвердить, оценить или повторно открыть в установленный период.

6.2. Правила ответа

Факты о балансе, чеках, транзакциях, картах, купонах, сроках и статусах берутся только из backend API или утвержденной KB.

AI не имитирует успешное действие. Если операция не выполнялась backend-сервисом, ответ не должен утверждать обратное.

При конфликте между KB и API приоритет имеет актуальный API для персонального статуса, а кейс получает diagnostic flag.

Низкая уверенность, отсутствие источника, сбой API, чувствительная тема или негативный повтор переводят кейс к человеку.

Системные prompts, models, temperature, thresholds и KB version сохраняются вместе с AI event для аудита без хранения секретов.

Статья KB содержит project/region, category, locale, title, body, structured answer blocks, source URL/document, effective dates, owner, reviewer, version, status и superseded_by. Публикация выполняется после review. Индекс обновляется атомарно; rollback возвращает предыдущую approved version.
